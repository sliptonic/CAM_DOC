Machine Configuration

Introduced in 26.3. A Machine describes a real CNC machine to FreeCAD: its axes and their limits, its kinematic layout, its toolheads, which Post-Processor it needs, and how its G-code should be formatted. The definition lives in one JSON file with the .fcm extension. Assign a Machine to a Job and post-processing runs through the machine-based pipeline; everything the old system scattered across script flags and argument strings sits in this one file.

This page covers configuring machines: the editor, the file format, and how machine settings interact with the Job. To write a new Post-Processor for the machine-based system, see Writing a Machine-Based Post-Processor. For the command-page summary, see CAM Machine.

Overview

introduced in 26.3: A Machine describes a physical CNC machine to the CAM workbench. The description holds the axes and their limits, the kinematics, the Toolheads, the Post-Processor (Post) and the format of the G-code output. One JSON file with the .fcm extension stores the description. A Job that has a Machine uses machine-based post-processing.

This page explains the Machine Editor, the .fcm file format, the validation of a Machine, and the Machine settings in the Job. Machine is the command page and lists the common Post-Processor Properties. Writing a Machine-Based Post-Processor explains how to write a Post for this system.

How the pieces fit

A Job stores only the machine’s display name in its Machine property. At post time FreeCAD looks the name up (case-insensitively) among the available .fcm files, loads the file, and reads postprocessor.file_name from it to pick the Post-Processor. The machine’s output options, processing options, and post properties then configure that Post-Processor. A Job with no Machine still uses the legacy flow — its PostProcessor and PostProcessorArgs properties — so both systems coexist.

Configuration reaches the Post-Processor in a fixed priority order. Later stages win:

  1. Values stored in the machine’s .fcm file (postprocessor.properties).

  2. Schema defaults, for any property the file doesn’t mention.

  3. Job-level overrides from the Job’s PostProcessorPropertyOverrides property.

  4. Per-export overrides entered in the Post Processing dialog.

A Job stores only the display name of its Machine, in the Machine property. At export, the workbench finds the .fcm file whose machine.name field matches that name. The comparison ignores case. The postprocessor.file_name key of the file selects the Post. The output options, the processing options and the Post-Processor Properties of the Machine then configure that Post.

A Job with no Machine uses its PostProcessor and PostProcessorArgs properties. The two systems exist together.

A Machine starts in the Machine Editor as a new Machine, as a copy of a Machine Template, or as an import from an MTConnect agent. The Machine Editor accepts an imported Machine that is not yet saved to a file.

Where machine files live

User machines

.fcm files in the Machines folder of the CAM asset directory (by default <user application data>/CamAssets/Machines/). These are the machines offered in the Job task panel and the Post Processing dialog. The file is named after the machine with spaces replaced by underscores (My Router → My_Router.fcm), but the display name always comes from the machine.name field inside the file.

Add-on machines

Any installed add-on whose package.xml declares a machine content item contributes the .fcm files of the declared subdirectory as read-only templates, grouped under the add-on’s name (the FreeCAD/Machines add-on in the Addon Manager is the community collection). Subdirectories nest to any depth in the template picker. Selecting a template copies its settings into your own machine, so an add-on update never silently changes your configuration. An add-on can be hidden with an ADDON_DISABLED file in its folder; ALL_ADDONS_DISABLED in the Mod folder hides them all.

Built-in templates

The editor’s Type presets (below) generate standard 2- to 5-axis configurations without any file. A Machine/machines folder inside the CAM module is also scanned for shipped .fcm templates.

Saved Machines

Saved Machines are .fcm files in the Machines folder of the CAM asset directory. The default location is <user application data>/CamAssets/Machines/. The Job task panel and the Post-Processing Dialog offer these Machines.

The file name is the Machine name with each space replaced by an underscore: My Router becomes My_Router.fcm. The display name always comes from the machine.name field in the file.

Add-on Machine Templates

An installed add-on whose package.xml declares a machine content item supplies the .fcm files of the declared folder as read-only Machine Templates. The Template list groups them by the add-on name. Folders nest to any depth in the list. The FreeCAD/Machines add-on in the Addon Manager is the community collection.

The selection of a Machine Template copies its settings into your own Machine. An update of the add-on does not change your Machine.

A file named ADDON_DISABLED in the add-on folder hides that add-on. A file named ALL_ADDONS_DISABLED in the Mod folder hides all add-ons.

Built-in Machine Templates

The Type values of the Machine Editor make standard 2-axis to 5-axis configurations without a file. The Machine Editor also reads .fcm Machine Templates from the Machine/machines folder of the CAM module.

The Machine Editor

Open the editor from New Machine on the General tab of the Job task panel, or from Edit  Preferences  CAM  Assets  Machines with Add and Edit. It has three tabs. The Postprocessor and Options tabs are hidden if the boolean parameter Mod/CAM/EnableMachinePostprocessor is set to false (it defaults to true).

Open the Machine Editor from one of these locations:

  • New Machine on the Output tab of the Job task panel.

  • Edit  Preferences  CAM  Assets, in the Machines group, with Add or Edit.

  • Import… in the same Machines group, after an MTConnect import. Machine gives the import procedure.

The Machine Editor has four tabs: Machine, Toolheads, Postprocessor and Options. The Postprocessor and Options tabs are hidden when the boolean parameter Mod/CAM/EnableMachinePostprocessor is false. The default of the parameter is true.

Below the tabs are the buttons Edit as Text, Validate, Save and Close. Save writes the .fcm file. Close discards the changes.

Kinematics holds two capability flags — TCP Supported (the controller does tool-center-point control, e.g. G43.4) and DWO Supported (dynamic work offsets, e.g. G54.2) — plus free-form notes.

Every axis has:

The Kinematics group has three controls:

  • TCP Supported: the control does tool-center-point control, for example G43.4. Default: unchecked.

  • Rotation Strategy: how the control runs an Operation on a tilted Work Plane. Values Not declared, Dynamic work offset (DWO), Tilted work plane (TWP), Post transform (not available yet). Default: Not declared.

  • Kinematics Notes: free text.

With DWO, the Post commands the rotary axes and the control applies its pivot offsets. With TWP, the Post declares the plane and the control positions the rotary axes. The command that declares the plane comes from the Post, not from the Machine. A Machine with rotary axes and no strategy cannot post an Operation on a tilted Work Plane. Machine lists the conditions that the export checks.

An MTConnect import writes one line with the source of the import into Description. The import writes the same line into Kinematics Notes, then the text "Import assumptions:" and one line for each assumption. Examine these assumptions before you save the Machine.

Rotary axes add three fields that control how angles come out in G-code:

  • Solution preference — when two rotary solutions reach the same orientation, prefer shortest, positive, or negative motion.

  • Allow flip — permit the 180°-flipped solution when it keeps motion inside the limits.

  • Wrap strategy — what to emit as an axis accumulates whole revolutions:

    • unwound — monotonic angles, growing without bound (4613.86°). For controllers that treat the rotary like a linear axis.

    • modulo — angles kept in [0°, 360°). For indexers, and any controller where direction across the wrap doesn’t matter.

    • rezero — angles in [0°, 360°) with a G92 A0 injected at each full revolution and a closing G92.1 to clear the offset. For shortest-path wrapping controllers (LinuxCNC wrapped rotary) when continuous direction matters.

Toolheads is a tabbed list — a machine can carry several. Each has a type (rotary, laser, waterjet, plasma), which sets its capability profile, plus min/max RPM, maximum power (kW), tool change mode (manual or automatic), flood and mist coolant availability, a coolant delay, and a wait time after start. Type-specific extras: laser wavelength and focus range, waterjet pressure, plasma amperage.

A rotary axis has three more fields. These fields control the angles in the G-code.

  • Solution Preference: when two rotary solutions give the same orientation, the preferred motion. Values shortest, positive, negative. Default: shortest.

  • Allow Flip: permits the solution that is turned 180° when that solution keeps the motion in the limits. Default: checked.

  • Wrap Strategy: the angle output when an axis turns through full revolutions. Default: unwound.

    • unwound: the angle increases without a limit, for example 4613.86°. Use this value for a control that moves the rotary axis as a linear axis.

    • modulo: the angle stays in the range 0° to 360°. Use this value for an indexer, or when the direction across the wrap is not important.

    • rezero: the angle stays in the range 0° to 360°. The Post adds G92 A0 at each full revolution and G92.1 at the end. Use this value for a control that wraps on the shortest route, when a continuous direction is necessary.

Toolheads tab

The Toolheads tab is the second tab of the Machine Editor. A Machine can have more than one Toolhead.

  • Add Toolhead adds a Toolhead. Each Toolhead has its own tab. The close button of the tab removes the Toolhead.

  • Toolhead type: Rotary, Laser, Waterjet, Plasma or Wire EDM. The type sets the capabilities of the Toolhead.

  • Common fields: minimum and maximum rpm, maximum power in kW, tool change mode (manual or automatic), coolant flood and mist, coolant delay, and the wait time after start.

  • Fields for one type: laser wavelength and focus range, waterjet pressure, plasma amperage.

A Wire EDM Toolhead moves along Z and the table supplies X and Y. This Toolhead has power control and pulse control, uses water, and has no speed control.

The Sanity Check compares each commanded Spindle Speed with the rpm range of a rotary Toolhead. Machine gives the conditions.

Postprocessor tab

Pick the Post-Processor here. The combo lists only machine-based posts — the ones declaring POST_TYPE = "machine" — never legacy script posts. Below the combo the editor renders one widget per entry of the selected post’s property schema: file extension, preamble, postamble, safety block, the pre/post G-code blocks, supported commands, precision settings, and any post-specific properties (LinuxCNC adds its blend mode, the plasma post its pierce and cooling delays). Widgets and defaults come straight from the post’s schema, so a new post needs no editor changes to be fully configurable. Properties marked runtime in the schema don’t appear here — they’re per-run choices offered in the Post Processing dialog instead (see property visibility).

Only values you actually change are written to the .fcm file. Everything else stays at the schema default, so posts can improve their defaults later without stale copies in every machine file.

Select the Post in the list at the top of the tab. The list holds the Posts on the post search path that the machine-based system can run, for example generic, grbl, linuxcnc and fanuc. Post-Processor Genealogy lists the Post classes.

Below the list, the tab shows one control for each Post-Processor Property of the selected Post that has Machine scope or Job scope. The controls and the defaults come from the property schema of the Post. A new Post needs no change to the Machine Editor.

  • A Machine-scope property is edited on this tab only. Examples are File Extension, Preamble, Postamble, Safety Block, the G-code blocks, Supported G-code Commands and the precision properties.

  • A Job-scope property gets its default on this tab. Examples are Allow tool-change and the blend mode and blend tolerance of the linuxcnc Post. The Options tab of the Post-Processing Dialog overrides the default for one run.

  • A Run-scope property, such as Show Pre-processing Dialogs, does not appear in the Machine Editor.

The common properties include these entries:

  • Ignore G-code Commands: one command on each line. The Post accepts a command in this list and removes it from the output. The command is not necessary in Supported G-code Commands. Default: empty.

  • Drill Cycles to Translate: Default: G73, G81, G82, G83, G85, one on each line.

  • Generated Parameter Order for GCode: Default: XYZABCUVWFSIJKTQRPDHL.

  • Post-Tool Change: G-code written immediately after the tool change (M6), before the G43 line and before the spindle start.

  • Tool Return after tool changes: G-code written immediately after the spindle start that follows a tool change.

  • Pre-Rotary Move and Post-Rotary Move: G-code written before and after the rotary axes move.

  • Tilted work plane: control positions the rotaries, Tilted work plane: declare, Tilted work plane: align and Tilted work plane: cancel: the lines that the Post writes for the TWP strategy.

Machine describes every common property. Postprocessor Customization describes the properties of each Post.

The .fcm file stores only the values that you change. All other properties use the schema default. A Post can thus change a default and each Machine file gets the new default.

Text view and validation

Edit as Text changes the Machine Editor switches the whole dialog to a JSON text view of the full file. The same button changes the editor back.

editor of the file. Save writes the .fcm; Close discards.

Validate examines the Machine for problems that stop the load or that silently drop settings. A Validation dialog shows the result:

  • "No problems found." when the Machine has no errors and no warnings.

  • The number of warnings, or the number of errors and warnings. The details of the dialog list each finding with its severity.

  • "Invalid JSON" or "This machine does not load", with the cause, when the text view does not hold a correct Machine.

In the text view, the validation also compares the JSON text with the Machine that the loader makes from it. This comparison finds keys that the loader does not read. In the tab view, the comparison does not run, because no file text exists for the comparison.

Key points about the format:

These rules apply to the format:

  • postprocessor.file_name is the module name without _post.py. The value stem: linuxcnc loads linuxcnc_post.py and instantiates its Linuxcnc class.

  • postprocessor.properties holds only the changed values. Each other property of the schema is sparse. Only user-changed values belong here; every property the post’s schema defines gets its schema default at load. The properties of one Post, such as blend_mode of linuxcnc, load time. Post-specific properties (like the LinuxCNC blend_mode) go in the same object.

  • kinematics.rotation_strategy is one of none, dwo, twp or post_transform. Default: none. When the key is absent, "dwo_supported": true selects dwo. A saved file contains the two keys.

    • dict.

  • Each joint is [origin, axis_vector]. The object form {"origin": […​], "axis": […​]} is also accepted. The axis type angular is accepted accepted, as is the older axis type name angular for rotary.

  • A rotary axis can also have Rotary axes may also carry solution_preference, allow_flip , and wrap_strategy. The wrap_strategy values are unwound, modulo and rezero.

  • toolhead_type is one of rotary, laser, waterjet, plasma or wire_edm. A different value stops the load of the Machine.

  • A Toolhead accepts the keys Toolheads accept type-specific keys: laser_wavelength, laser_focus_range, waterjet_pressure and , plasma_amperage.

  • processing.return_to is an optional [x, y, z] array.

  • A file with the flat layout Older flat layouts (a boolean header, top-level line_numbers, axis_precision, output_comments) loads. Save writes still load; saving rewrites them in the nested structure of the example.

Hand-editing the JSON is fine — the editor’s Edit as Text view exists for exactly that — but keep it valid; a machine that fails to parse simply won’t load.

You can edit the JSON manually in the text view or in a text editor. A file that is not correct JSON does not load.

Validation from the command line

The checks of Validate also run from the command line, on one file or on a folder of .fcm files:

FreeCADCmd path/to/Mod/CAM/Machine/models/validate.py --pass MACHINES_DIR

--pass is required, because FreeCAD opens each argument after the script as a document when --pass is absent.

A finding has one of three severities:

  • ERROR: the definition does not load, or loads into a Machine that is not usable. The file causes are incorrect JSON, an unknown Toolhead type and a broken kinematic chain. The content causes are an empty Machine name, a Machine with no axes and a Post that cannot be found. An axis whose minimum limit is not less than its maximum limit is an error. A Machine name that a second file also uses is an error.

  • WARNING: the file holds keys that the loader does not read, the Machine names Post-Processor Properties that the Post does not declare, or the Machine has no Toolheads.

  • INFO: the model has fields that the file does not contain.

These options are available:

  • --strict: a warning gives exit code 1.

  • --json: the output is JSON.

  • --verbose: the output includes INFO findings and the files with no findings.

  • --no-postprocessor-check: the validation does not look for the Post.

The exit code is 0 when no error was found, 1 when an error was found, and 2 when no .fcm file was found.

Machine settings in the Job

Select the Machine in the Machine list on the Output Set the machine on the General tab of the Job task panel, or write the Machine property directly. The first entry of the list, "(Legacy post-processor)", leaves the Job without a Machine and empties the Machine property.

With a machine assigned:

  • The Job’s PostProcessor and PostProcessorArgs properties are ignored. The machine decides the post and its configuration.

  • The Post Process command opens the multi-tab Post Processing dialog and runs the machine-based pipeline (export2()).

  • Machine limits, toolhead RPM range, and any post-specific checks feed the sanity system — the dialog’s Warnings tab and Quick Validate.

With a Machine selected:

  • The Output tab hides the rows for the Post-Processor and its arguments. The Machine holds the Post and its settings.

  • The Job’s PostProcessor and PostProcessorArgs properties are ignored.

  • The Post Process command opens the Post-Processing Dialog and runs the machine-based sequence (export2()).

  • The axis limits, the rpm range of the Toolhead and the checks of the Post supply Squawks to the Sanity Check. The Warnings tab of the dialog and Quick Validate show them.

  • The Sanity Check gives a WARNING Squawk when the rotary axes move between Operations and Pre-Rotary Move is empty.

Job-level overrides

The Job property PostProcessorPropertyOverrides holds a JSON object of Post-Processor Properties dictionary of post properties that this Job overrides. One Machine file can thus serve many Jobs that have small differences.

overrides, so one machine file can serve several Jobs with small variations: 
{"file_extension": "tap", "post_operation": "M9"}

Two rules. Keys must exist in the post’s property bundle — unknown keys are warned about and dropped. And the string must be valid JSON — a malformed value stops post-processing with an error rather than silently ignoring your settings. Job templates save and restore both Machine and these overrides.

{"tool_change": false}

Two rules apply:

  • Each key must exist in the properties of the Post. The export gives a warning for an unknown key and drops it.

  • The text must be correct JSON. Incorrect JSON stops the export with an error.

A Job Template saves and restores the Machine property and these overrides.

Per-export overrides

The Post Processing dialog offers one more layer, applied only to that export and never saved:

  • The Overview tab shows the post’s runtime properties (per-run choices like a dry-run flag or blend mode).

  • The Options tab shows the machine’s full output and processing groups, editable in place.

  • The machine combo lets you post against a different machine than the Job’s, once.

The Post-Processing Dialog gives one more level of overrides for one export:

  • The Overview tab shows the Run-scope properties of the Post, such as Show Pre-processing Dialogs. These values are not stored.

  • The Options tab shows the output and processing groups of the Machine. You can edit them there for the export.

  • The Options tab also shows a Postprocessor Properties group with the Job-scope properties of the Post. The group starts with the Machine values and the Job overrides applied.

  • The Machine list lets you export with a different Machine from that of the Job, one time. The first entry of the list is "(Legacy post-processor)".

The dialog does not show Machine-scope properties.

Scripting

from Machine.models.machine import Machine, MachineFactory, RotationStrategy
from Machine.models.validate import validate_file

 MachineFactory

 m = Machine.create_3axis_config()          # or create_4axis_A_config(), create_AC_table_config()
 create_AC_table_config(), ...
 m.name = "Shop Router"
m.postprocessor_file_name = "linuxcnc"
m.postprocessor_properties["file_extension"] = "ngc"
m.output.comments.enabled = False
m.linear_axes["X"].max_limit = 840
 m.kinematics.rotation_strategy = RotationStrategy.NONE
 MachineFactory.save_configuration(m)       # writes <CamAssets>/Machines/Shop_Router.fcm

 for finding in validate_file(MachineFactory.get_config_directory() / "Shop_Router.fcm"):
    print(finding)

# job is an existing CAM Job object
 job.Machine = "Shop Router"

from Path.Post.Processor import PostProcessorFactory
post = PostProcessorFactory.get_post_processor(job, "linuxcnc")
sections = post.export2()                  # [(section_name, gcode), ...]

validate_machine(machine) examines a Machine object that is not saved. validate_paths(paths) examines files and folders, and also finds a Machine name that two files use.
